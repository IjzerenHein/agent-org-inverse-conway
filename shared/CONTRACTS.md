# Contracts: the shared interfaces of the kit

For whoever repairs a skill. Everything more than one artefact depends on is defined here once. Do not redefine it in a skill: copy nothing by hand, name the asset or include the sentence by marker. Where this file and a skill disagree, this file wins; where this file and `docs/process.md` disagree, the process wins and this file has a bug.

## Conventions

- **Generated files, never edited by hand.** Every destination in `manifest.json`: the template copies under `skills/*/assets/`, `agents/*.md`, and the `*-brief.md` copies. Edit the source in `shared/` and run the sync script.
- **Sentences.** Include one by writing `<!-- shared:KEY -->` and `<!-- /shared:KEY -->` on their own lines in a SKILL.md or a reference file; the sync script fills the text. Never retype a shared sentence. The markers cannot be used inside YAML, and a ledger entry should not carry marker comments into a project, so some files hold a hand-kept short form. Change each together with its sentence; this is the full list:
  - `profile-template.yml`: `casing` (header comment), `approved-profile` and `proposed-profile` (comment under `approval:`, with the definition of `last_approved_in`), `ledger-entry` (comment at `artefacts.ledgers`), `p9-lookup` (the Lookup comment at P9, and the comment at `release_surfaces[].paths`).
  - `pending-acceptance-entry-template.md`: `pending-acceptance-close` (the `status` comment).
  - `attestation-template.md`: `judged-attestation` (the `confirmed` comment and the body paragraph) and the attestation clause of `blocked-question-return` ("a change of its own").
  - `fact-entry-template.md`: the `confirmed` rule of `judged-attestation`, applied to `attestation.confirmed`.
  - `question-entry-template.md`: `questions-close` (the `closed-by` comment and the body comment).
  - `experiment-entry-template.md`: the expiry rule of item 21 below, which has no sentence key.
  - `spec-template.md`: `observed` and `judged-attestation` (the acceptance comment), `shipped-spec` (the `depends-on` comment), `p9-lookup` (the `surfaces` comments), `blocked-question-return` (section 9). It uses the markers for `approved-spec` only; the spec's author deletes the marker lines with the other HTML comments.
  - The briefs restate in their own steps: builder step 2 (`approved-spec`, `shipped-spec`), builder step 5 (`p9-lookup`), the builder's paragraph on `blocked` (`blocked-question-return`), checker step 6 (`judged-attestation`), spec-critic check 25 (`p9-lookup`).
- **Casing** (key `casing`). `profile.yml` is snake_case. Everything else the kit defines is kebab-case, the roles' structured output included.
- **Asset names.** Every template is `<thing>-template.md` (or `.yml`); every role brief is `<role>-brief.md`. Renames and deletions this forces: `skills/adr/assets/question-entry.md` and `fact-entry.md` (replaced by the `-template` copies), `skills/adr/assets/research-brief.md` (replaced by `researcher-brief.md`), `skills/spec/assets/critic-brief.md` (replaced by `spec-critic-brief.md`), `skills/retro/assets/escape-template.md` (replaced by `escape-entry-template.md`), `skills/lens-placement/assets/placement-table.md` (rename to `placement-table-template.md`), and the old per-skill variants of `question-entry-template.md` and `finding-entry-template.md` (overwritten by the sync).
- **Ledger entries** (key `ledger-entry`). One file per entry, `<ledgers>/<kind>/YYYY-MM-DD-slug.md`, frontmatter discriminator `ledger: <kind>`, `id` equal to the file name. An attestation is the one exception to the name: `<ledgers>/attestations/<acceptance id>-<short commit>.md`; its `id` still equals its file name.
- **Changes of their own.** Whatever a session writes around a builder (the questions entry and section 9 row of a `blocked` report, the findings entries made from `learned`, a prepared attestation, an `expiry-extension` row) lands in a change of its own on the default branch, never on the builder's branch. Otherwise the guard sees paths outside `touches` and the checker reports the spec as changed in the diff. A skill always writes from the kit template. The sentence "match an existing ledger's format" goes from every skill: it is in none.
- **Profile path.** Fixed at `docs/process/profile.yml` for every skill and role; no caller passes another path. Every skill and role reads it first and takes paths from `artefacts:`.
- **Person words.** "The owner" in adopt means whoever holds decision rights over the profile (`approval.approver`); adopt says so in its first paragraph. The harness owner is `dials.P4.role_matrix`, role `harness owner`.

## The build skill (new, thin)

`skills/build/`: carries the hop from an approved spec to the release gate (finding 22). It writes no code and no spec. Order: (1) confirm the spec is approved (key `approved-spec`); (2) start one builder with the spec path only, on a branch that contains the default branch's current version of the spec and of every entry its section 9 points to; (3) on `blocked`, read `blocked.kind`. `precondition`: report `reason` to the user and stop; write no questions entry and no section 9 row, because the thing that must happen first is already open somewhere. `question`: write the questions entry and the section 9 pointer (key `blocked-question-return`), in a change of their own on the default branch, never on the builder's branch, and stop; a `role` of `profile approver` goes to `approval.approver` and its answer arrives through the profile skill, row update; (4) file each `learned` item as a findings entry with `status: hypothesis`, `found-by: builder (<spec id>)`, the builder's `claim` copied unchanged as the heading and its `pointer` under Evidence, never reworded (T1), again in a change of their own on the default branch; (5) wait for machine evidence; (6) start the checker from a base checkout with the five inputs, kind-specific inputs as listed in the checker brief, input 4; (7) for each `judged` id the checker leaves at `awaiting attestation`, prepare an attestation file with `scores`, `verdict` and `confirmed` empty for the value owner, in a change of its own; (7b) once the attester has confirmed it and it has landed, start a fresh checker with the attestation as evidence, read at the ref where it landed; (8) hand the checker's report and the evidence ids to the gate the profile names, as a packet of paths and ids, and only a report whose `overall` is not `incomplete`: no id may still be at `awaiting attestation` (V1). It includes the keys `approved-spec`, `shipped-spec`, `blocked-question-return`, `pr-spec-line`, `judged-attestation`, `ledger-entry`, `missing-profile`, `proposed-profile`, `walls`, `casing`. Assets, all generated: `builder-brief.md`, `checker-brief.md`, `question-entry-template.md`, `finding-entry-template.md`, `attestation-template.md`.
